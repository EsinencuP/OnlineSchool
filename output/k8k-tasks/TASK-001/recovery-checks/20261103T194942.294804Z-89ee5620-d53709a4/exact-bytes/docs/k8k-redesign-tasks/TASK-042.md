6. Деньги остаются точными decimal strings/существующим Decimal; никаких `Number`/`parseFloat` для сумм. Не смешивать валюты, аванс, нераспределённые средства семьи, остаток уроков и ожидающие поступления. Чужие дети смешанного портфолио/семьи не раскрываются.

Спор/предварительное начисление/подтверждённая выплата различаются; личные обещанные обязательства не отменять молча.
8. У ученика нет общего чата/«Моих обращений»/пункта «Сообщения» и отдельного центра уведомлений: только колокольчик. Официальные внешние контакты только из разрешённой CRM-проекции. Спецформы переноса/спора остаются в уроке. Новые внешние организационные автонапоминания семье не вводить.

## 5. Предметные правила и сохранение поведения

- Счётчик включает только подтверждённые LessonActualOutcome с действительным CONDUCTED состоянием; plan/start/report, отмены и неподтверждённые события не считаются.
- Считать отдельно student+subject через историю enrollment; новая подписка, перерыв или смена teacher не сбрасывают цикл.
- 4 проведённых → пересмотр навыков,8 → образовательный отчёт; обязательного отдельного отчёта на4-м уроке нет.
- Наступление контрольной точки и её подтверждение/SkillSnapshot различаются; автоматическая очередь не выставляет навыки и не публикует отчёт.
- Использовать существующие ProgressCheckpoint/SkillSnapshot/SQL guards; не создавать дублирующую таблицу4/8 и второй независимый счётчик.
- Ретроисправление проведённого урока — открытая EDU-RETRO-01 зависимость: не удалять/перенумеровывать опубликованные snapshots/reports автоматически.
- Сроки пересмотра2 рабочих дня и отчёта3 рабочих дня сохраняются; календарь рабочих дней берётся из утверждённой конфигурации, не из произвольного браузерного timer.
- Дедупликация исходного события и own teacher assignment обязательны; открытый dashboard не является условием создания очереди.

## 6. Контракты, данные и совместимость

- Новые teacher checkpoint reads/trigger workflow описываются здесь. Read DTO: student/enrollment/subject, type, confirmedCount, triggeringOutcome, status, revision/basis, due information и безопасная связь с предыдущими публикациями.
- Учитель определяется сессией; target subject и checkpoint ID проверяются по текущему назначению. Событие системы несёт durable source ID, не произвольное число уроков от клиента.
- Физический checkpoint связан с реальным outcome; count не подменяется произвольным номером календарного урока. Сохранённое основание позволяет объяснить происхождение точки.
- Повтор outbox/job не дублирует точку/задачу; unknown/retry имеет ограниченный lifecycle и аудит. Частичная ошибка не выдаётся за завершённый педагогический контроль.
- При retro mismatch возвращается честный review-required и блокируются зависящие автоматические изменения; точный окончательный алгоритм перерасчёта не объявляется утверждённым этим заданием.

Точные имена новых planned DTO/operation/props запиши в коротком design note этого TASK до реализации и соблюдай существующие namespace/style. Planned нельзя выдавать за уже существующий API. Найденный существующий сервис переиспользуй. Generic UI не принимает бизнес-решения. Существующий авторитетный источник не копируется во второй реестр.
