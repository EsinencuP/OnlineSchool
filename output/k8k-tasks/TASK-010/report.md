## Что уже существовало

В CRM уже работают таблицы, фильтры и курсоры. Leads содержит семь полей и обычную ссылку
на заявку, принимает фильтры из URL и получает items/nextCursor. Порядок сервера фиксирован
по createdAt/id DESC. Отдельный summary возвращает агрегаты стадий. Доска группирует
загруженные записи. Students принимает name/nextLesson/subscriptionEnd и возвращает cursor
без total. Tasks также использует курсор. [Исходный инвентарь и проект контракта](design-note.md)

## Что изменено

- packages/ui/src/tables.tsx и tables.css добавляют DenseTable, ListRow и KanbanColumn.
  TanStack Table использует core row model и ручные режимы сортировки, фильтрации и пагинации.
  Приложение передаёт строки в серверном порядке. Заголовки поддерживают keyboard activation,
  aria-sort отражает применённую сортировку. Выбор хранится у вызывающего кода по ID.
- DenseTable выводит caption, заголовки, число показанных записей, отдельно total и hasMore.
  Курсор остаётся у приложения. На мобильном экране таблица прокручивается внутри
  фокусируемой области. Ссылки остаются доступны с клавиатуры, значения оборачиваются.
  При 403 и завершении сессии приватные строки, ссылки и пагинация удаляются из DOM.
- ListRow предоставляет слоты для ссылки, полей и действий. KanbanColumn показывает переданный
  count или неизвестное значение, pending и список. Количество загруженных элементов
  не используется как общее число стадии.
- apps/manager-web/src/components/lead-table.tsx подключает DenseTable к K8K Leads. Используются
  действующие поля, ссылка и cursor. Заголовки K8K таблицы локализованы на RU/RO. Фильтры формы
  восстанавливаются из URL при Back. Сортировка заголовков доступна только там, где вызывающий
  код объявил её направления. Контракт Leads сохраняет фиксированный серверный порядок.
- apps/manager-web/test/ui-tables содержит fixtures с серверным сортированием и фильтрацией
  всего синтетического набора. Отдельный сценарий использует настоящий компонент Leads,
  RequireManager, SDK GET и router с подменёнными ответами.
