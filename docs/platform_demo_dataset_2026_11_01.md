Все пять учеников и заявка Евы Кожокару на бесплатный пробный урок английского
относятся к портфолио Тамары. Директор — Паша. Заявка остаётся новой:
менеджер связывается с контактом и согласует время; сам урок не выдуман.
Две ручные задачи: подобрать преподавателя Олегу и напомнить Софии о ДЗ
(последняя намеренно просрочена на час для демонстрации дашборда).
Дополнительно создаются штатные задачи первого контакта и назначения преподавателя по заявке.
Каждому из четырёх учащихся выдано отдельное домашнее задание.

Скрипт `scripts/provision-platform-demo.mjs` имеет две независимые атомарные фазы:

1. `base`: новые сотрудники/преподаватели с паролями, CRM, направления,
   назначения, доступность преподавателей, ДЗ, заявка, задачи, Audit + Outbox.
2. `paid`: только при отдельном точном разрешении в защищённой среде сборки.
   Штатные Finance-команды регистрируют и подтверждают директором демонстрационные
   поступления, публикуют распределения в Ledger, затем создают управляемые абонементы,
   оплаченные права и аккаунты учеников. Никакой реальной оплаты эти записи не удостоверяют.
   Штатный Schedule бронирует по три будущих занятия каждому ученику (12 уроков)
   с проверками прав, преподавателя, доступности и пересечений.
   Анне отправляется приветствие, Софии — напоминание о ДЗ, оба только `IN_APP`.

Предложенный финансовый пример: 3200 + 2700 + 1400 + 1200 = `8500.0000 MDL`,
22 оплаченных права, сроки 30/30/14/7 дней. Включение фазы `paid` требует ответа
владельца на отдельный вопрос о демонстрационных проводках; без него она не запускается.
CRM-ученик без опубликованного распределения не получает аккаунт.

Guard требует production существующего проекта, режим входа по паролю,
точную метку, восемь ожидаемых логинов с scrypt-хешами и окно не более 30 минут.
На завершённую фазу повторный запуск возвращает `already-provisioned`,
не перезаписывая последующие изменения владельца. Чужой существующий логин — ошибка,
а не сброс пароля. SERIALIZABLE повторяется только при P2034, максимум три попытки.
Закрытый финансовый период не переоткрывается. Пароли/строки подключения в лог не выводятся.

Внешние email/SMS не отправляются, Meet-ссылки не подделываются,
посещённые уроки, списания и реальная выручка не создаются.
Системное уведомление о поступлении до появления аккаунта честно сохраняет
`FAILED / NO_DELIVERY_CHANNEL`; операция подтверждения при этом завершается.

Проверки перед запуском: четыре адресных теста guard/коллизий/повторного запуска,
ESLint изменённых файлов, typecheck worker. Результат применения и live-проверки
добавляется после выполнения, без утверждения полного регрессионного GO.

На первом live-прогоне обнаружена исходная ошибка MGR-02: карточка ученика читает
`education_reports` и `progress_checkpoints`, но runtime-роль не имела SELECT на эти
таблицы. Сам SQL успешно выполнен владельцем БД, обе проверки `has_table_privilege`
для runtime вернули false. Отдельная новая миграция добавляет только эти два SELECT;
схема, прежние миграции, права на запись и фильтры портфолио сохраняются.
Проверка разрешений включена в штатный read-only deployment smoke.
