# OnlineSchool Independent QA

Откройте `D:\OnlineSchool` как проект Codex и в новом чате вызовите `$qa-status`. Команды доступны в [COMMANDS.md](COMMANDS.md). Для проверки установки запустите `$qa-cycle --self-test` или `node qa/scripts/qa.mjs cycle --self-test` из корня. Этот прогон поднимает короткоживущую синтетическую страницу и использует реальный Codex CLI, Playwright MCP и Chromium.

## Требования

- Node.js 24 и Git из проекта, Codex CLI с входом ChatGPT и загруженными проектными Skills. Установщик проверял Codex CLI 0.171.0-alpha.13 и Playwright MCP 0.0.83.
- `codex mcp get playwright` должен показать локальный stdio-сервер. На этой машине переиспользуется подключённый сервер. Для другой машины используйте пример [playwright.toml.example](fixtures/playwright.toml.example), если сервера ещё нет. Поддерживаются официальный JS entry point Playwright MCP через Node и точная версия npm-пакета через npx. Для headless требуется установленный Chromium либо Chrome, доступный используемой версии Playwright MCP.
- Координатор выбирает профиль из проектного TOML и запускает отдельный ephemeral Codex CLI с ChatGPT-аутентификацией. Есть также нативные определения агентов для Codex. Запуск вручную через нативный spawn наследует настройки другого чата. Ограничения [SECURITY_MODEL.md](SECURITY_MODEL.md) относятся к запуску через команды проекта.

## Сборка и аккаунты

1. Выберите подтверждённую сборку. Используйте отдельную синтетическую среду, например согласованный [локальный демостенд](../README.md#локальный-демостенд) или [Railway test](../infra/railway/README.md) через согласованный loopback-прокси. Проверьте происхождение БД, состояние миграции, отсутствие настоящих данных и внешних операций. Туннель не делает целевой стенд безопасным сам по себе.
2. Скопируйте [build.json.example](fixtures/build.json.example) в `qa/fixtures/build.json`. Укажите полный commit, идентификатор сборки, применённую миграцию, метку синтетической базы, QA origin и список изменений. Тот же JSON должен обслуживаться **этой сборкой** на `/.well-known/k8k-qa-build.json` как `application/json`. Установите marker в конфигурации развертывания стенда или через endpoint его локального прокси, привязанный к проверяемому инстансу. При смене сборки меняйте marker вместе с ней. Запись `writes: blocked` защищайте режимом самого стенда, а `synthetic-only` используйте только с изолированной БД и отключёнными внешними адаптерами.
3. Создайте четыре отдельных файла по [accounts.env.example](fixtures/accounts.env.example) в `qa/fixtures/` с именами `student_agent.env`, `teacher_agent.env`, `manager_agent.env`, `director_agent.env`. Используйте существующий утверждённый механизм provisioning и разные роли. Режим QA password-only может помочь проверить синтетический вход. Для сценария полноценного MFA нужна отдельная допустимая фикстура MFA. Никогда не копируйте рабочие учётные данные и `storageState`.
4. Запустите `$qa-cycle` с нужным `--gate`. Аудиты, доказательства и журнал будут сохранены локально. Справка по различиям между установочным и продуктовым прогоном есть в [QA_STATUS.md](QA_STATUS.md).

Матрицы находятся в [test-matrix](test-matrix/MASTER_TEST_MATRIX.md). Дополняйте соответствующую матрицу новым стабильным ID, наблюдаемым результатом и ссылкой на утверждённое требование. Отдельный цикл для изменения требований не нужен. Историю и уже выданные ID сохраняйте.

## Проверки проекта и работа с журналом

| Вид | Существующий вход |
|---|---|
| Unit и TypeScript | `pnpm test:unit`, `pnpm -r typecheck` |
| Lint и сборка | `pnpm -r lint`, `pnpm -r build` |
| Интеграция и миграции | Действующие jobs `integration-test`, `migration-syntax` в [CI](../.github/workflows/ci.yml) |
| Playwright и регрессия | Существующие `test:fnd:e2e`, `test:stu*`, `test:mgr*` и jobs Foundation/Manager. Проверяйте среду, которую использует целевой скрипт |
| Валидация координатора | `node --test qa/scripts/qa.test.mjs` и `node qa/scripts/qa.mjs cycle --self-test` |

Существующий CI остаётся источником автоматических проверок. В job `unit-test` добавлена проверка координатора без Codex, браузера и продуктовой БД. Ролевой AI-цикл запускается вручную после появления нужной сборки. Подключение CI к отдельной AI-сессии потребовало бы собственной интеграции и авторизации. В короткой задаче выбирайте только нужные проверки по [PHASE0_CHECKS](../PHASE0_CHECKS.md).

`qa/cycles/<id>/` хранит полный цикл. `qa/reports/<id>/` хранит одиночные аудиты. Внутри доступны исходные JSON, Markdown-сводка, скриншоты, пакет, журнал и отдельные ретесты. Вывод `status` включает текущие дефекты и принятые риски. Храните эту историю на закрытом носителе. В Git включены только правила игнорирования. Если процесс аварийно завершился, прежде чем удалить пустую `qa/cycles/.run-lock`, убедитесь, что предыдущий координатор и его дочерние Codex/Playwright процессы завершены.
