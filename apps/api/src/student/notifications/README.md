# STU-10 — внутренний колокольчик ученика

Состояние на 2026-10-28: код и адресные проверки готовы. PostgreSQL-проверка
отложена по решению владельца, принятому в STU-08. Миграция подготовлена после
STU-01–09, в рабочую БД не применялась. Деплой и сквозная приёмка не выполнялись.

## Контракт

| Маршрут                                                | Результат                                                                                       |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
| `GET /api/v1/student/notifications?page=1&pageSize=30` | items/total/unreadCount/page/pageSize; newest first (`created_at DESC,id DESC`), pageSize 1–100 |
| `GET /api/v1/student/notifications/count`              | `{unreadCount}`; один COUNT по таблице уведомлений, без JOIN или загрузки title/body/payload    |
| `POST /api/v1/student/notifications/read-all`          | 204, пустое тело ответа, включая повтор и cached replay                                         |
| `PATCH /api/v1/student/notifications/:id/read`         | 204; неизвестный, чужой, архивный или истёкший id — одинаковый 404                              |

Обязательны существующие session/STUDENT/context/initial-password/active-access
guards STU-01. Истёкший доступ получает 402, обязательная смена пароля — 403;
это сохраняет действующую политику STU-01. Все ответы no-store. POST/PATCH требуют
CSRF и UUID `Idempotency-Key`, допускают только пустое тело. Чтение фиксируется
в общей critical transaction с audit/outbox/idempotency; ошибка откатывает всё.
Контроллеров создания, удаления, редактирования текста или сброса read нет.

Типы ровно: HOMEWORK_REVIEWED, HOMEWORK_NEEDS_REVISION, LESSON_RESCHEDULED,
LESSON_CANCELLED, REPORT_READY, SUBSCRIPTION_EXPIRING, PAYMENT_CONFIRMED.
API возвращает общую временную ленту; клиент группирует её по `type`, сохраняя
newest-first контракт. unreadCount относится ко всем видимым уведомлениям,
а не текущей странице. Пустая страница сохраняет total/unreadCount.

Владелец и единый `read_at` определяются по Student.id (`studentProfileId`),
а не устройству или текущему StudentAccount. Первый read_at неизменяем;
повторная команда не обновляет его. Read-all сериализуется с созданием через
per-student advisory lock. События, пришедшие после read-all, остаются непрочитанными;
повтор того же Idempotency-Key их не поглощает. Прочтение уведомления не означает
прочтение образовательного отчёта, выполнение задания или завершение CRM-операции.

## Создание из бизнес-фактов

Другие сервисы используют `NotificationService.create(tx, sourceId)` из
`@online-school/api/notifications` (`NotificationModule` доступен для Nest DI).
Нельзя передать произвольного ученика, текст или ссылку: сервис загружает
канонический `StudentNotificationSource`, проверяет payload, строит фиксированные
публичные title/body и создаёт `StudentNotification`. В контроллерах вставок нет.
Доставка сейчас выполняется `StudentNotificationProjector` в `apps/worker/`.

Транзакционные AFTER triggers фиксируют только намерение доставки (source),
а не сам inbox. Поэтому откат бизнес-команды не оставляет уведомления, а остановка
воркера не теряет событие. Источники и привязка к ученику проверяются в SQL:

| Факт                                                                          | Событие / payload                                                                    |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Новая SubmissionReview ACCEPTED                                               | HOMEWORK_REVIEWED; homeworkId=delivery.id, reviewId                                  |
| Новая SubmissionReview NEEDS_REVISION                                         | HOMEWORK_NEEDS_REVISION; homeworkId, reviewId                                        |
| Изменение scheduled_at или scheduled_end_at существующего неотменённого урока | LESSON_RESCHEDULED; lessonId; первоначальное создание урока не уведомляет о переносе |
| Переход урока в CANCELLED                                                     | LESSON_CANCELLED; lessonId; отмена имеет приоритет над одновременной правкой времени |
| Публикация восьмиурочного отчёта учителем                                     | REPORT_READY; reportId; черновик не уведомляет                                       |
| Подтверждённый руководителем платёж и утверждённое распределение              | PAYMENT_CONFIRMED; paymentId, distributionId, subscriptionId                         |
| Окончание абонемента через 7/3 календарных дня ученика                        | SUBSCRIPTION_EXPIRING; subscriptionId, daysBefore, expiresAt                         |

Платёж адресуется ученику **получателя распределения** через subscription/enrollment,
а не `PaymentReceipt.student_id`, который может быть лишь контактным лицом.
Денежные суммы, данные других получателей, внутренние причины отмены, оценки,
комментарии учителя, содержимое ДЗ и отчёта, capability URLs в payload не попадают.
Новые права доступа и финансовые факты из уведомлений не создаются.

Повторы подавляются уникальным event_key: review/report id, lesson id+version+type,
distribution id; для напоминаний — subscription id+точный valid_to+порог.
Новая версия проверки/публикации или новое время окончания — новое событие.
Уведомление хранит исторический факт; актуальные детали открываются в своей сущности.

Воркер каждые 60 секунд подготавливает до 50 отсутствующих напоминаний по конечному
`valid_to` (NULL не заменяется выдуманной датой), использует timezone активного
ученического аккаунта, исключает отключённые/архивные профили. Проверка выполняется
в дни 7 и 3; при простое за весь этот календарный день пропущенное напоминание
задним числом не рассылается. Продление абонемента меняет ключ следующего эпизода.

Затем воркер за poll доставляет до 20 источников: `FOR UPDATE SKIP LOCKED`,
`NotificationService.create()`, delivered_at — одна короткая DB-транзакция.
Inbox id совпадает с source id; повтор после rollback безопасен, уже доставленная
или архивная запись не воскресает. Внешнего I/O в этой транзакции нет, поэтому
lease для отдельного межпроцессного эффекта не нужен. Ошибка откатывает доставку
и остаётся для повтора; в лог попадает только NOTIFICATION_POLL_FAILED.
Обработчик работает отдельно от finance/schedule/PDF poll, один на процесс;
shutdown останавливает новые claims и дожидается активной обработки.

Автоматических внешних сообщений семье нет (CON-08/B). Teacher commands и цикл
публикации отчётов STU-08/09 остаются отдельным teacher workflow; здесь подключены
его будущие подтверждённые записи. Ретроспективное заполнение старой истории при
миграции не выполняется: источники фиксируются с момента применения миграции.

## Хранение и проверка

В активной ленте максимум 500 последних записей и только события моложе 90×24 часов.
Каждое создание под student lock архивирует overflow и истёкшие записи в той же
транзакции; равные даты упорядочены по UUID. Периодический проход архивирует
истёкшие записи и без новых событий. List/count исключают истёкшие записи даже
при остановленном воркере. На точной границе 90 дней событие уже не видно.
`archived_at` неизменяем, архив исключён из count и read. Архив и source сохраняются
для защиты от повторной доставки; автоматического физического удаления истории нет.
Частичный индекс unread не содержит тела уведомления; активная лента имеет индекс
student_id/archived_at/created_at/id, очередь — частичный индекс недоставленных.

`pnpm test:stu10` содержит 54 unit/actual Nest HTTP/worker/SDK проверки с mock Prisma.
Проверены роли/сессии/CSRF, владение, no-store, paging/count, пустые 204 и replay,
rollback, первый read, новые события после read-all, публичные шаблоны и payload,
идемпотентная доставка, stop/drain и отсутствие блокировки других poll.
Это не доказательство SQL constraints или реальной конкурентной работы PostgreSQL.

Prisma validate/generate, API/worker/SDK build и целевой lint прошли. OpenAPI —
78 операций. pglast/libpg_query разобрал 28 SQL statements, пять PLpgSQL и одну SQL
функцию, 13 запросов с непрерывными параметрами. Подготовлены 10 read-only сценариев:
изолированная лента, paging, 500/501 записи, TTL, стабильный tie-break и часовой пояс
напоминаний. Тест `tests/integration/student-notifications-readonly.test.mjs` по решению
владельца **не запускался**; он использует виртуальные CTE, без fixture INSERT.

Доказательства: `infra/STU10_EVIDENCE.json`, `tests/evidence/stu10-sql-syntax.json`.
Для приёмки остаются реальная цепочка миграций/права/SQL binding, transactional
source triggers, конкурентные create/read-all и worker claims, 500/TTL/expiry на
PostgreSQL и end-to-end на рабочей среде. Полный FND-GATE остаётся открытым.
Дополнительные БД/ветки Neon/контейнеры и production-записи не создавались.
