## Утверждённые уточнения

- Пробный бесплатный, длится 50 минут; краткий фидбэк виден менеджеру;
  первый контакт — 120 минут. Значения конфигурируются через env, включая
  TRIAL_FEEDBACK_VISIBLE_TO_MANAGER. Неверная конфигурация отклоняется.
- При пропуске пробного по skipTrialReason переход IN_PROGRESS → AWAITING_PAYMENT
  создаёт CRM-ученика LEAD без аккаунта в той же транзакции.
- Ранее утверждённая финансовая привязка сохраняется: конверсия следует из
  опубликованного распределения FIRST_PAYMENT на абонемент ученика, а не из
  подтверждения поступления семьи. MGR-03 отдельно проверяет условия активации.

## Реализация и границы

Все десять HTTP-операций защищены ManagerRoute и текущим назначением. Анониму —
401, остальным ролям — 403, отсутствующей/чужой/нераспределённой заявке — одинаковый 404. managerId не принимается из HTTP. Мутации используют штатные CSRF и critical
commands, SERIALIZABLE с максимум тремя попытками. Проверка версии, запись,
Audit, Outbox, создание ученика/назначения/урока и задачи атомарны. Meet URL
проецируется после commit и не сохраняется в результате идемпотентной команды.

Дубликат означает только предупреждение, не автоматическое объединение. Проверка
контактов выполняется исключительно в своём портфолио; forceCreate отражается в
Audit. В списках телефон маскируется; чтение карточки пишет LEAD_PII_VIEWED.
SQL-блокировки и фиксированные запросы находятся в CRM data-access boundary
`modules/crm/lead-data.ts`; запреты raw SQL и финансовых/педагогических записей
в manager остаются включёнными. INV-02 дополнен моделями исходов урока.

При claim закрывается LEAD_FOLLOWUP; ASSIGN_TEACHER остаётся до назначения
пробного. Назначение закрывает обе задачи. overdue в списке означает любую
просроченную открытую задачу заявки; summary.overdueFollowups считает только
LEAD_FOLLOWUP. Задачи MGR-07 с leadId ведут в карточку заявки, studentId nullable.

Пробный не проверяет платный абонемент, не создаёт выдачу/потребление прав и Ledger.
DB запрещает потребление прав для TRIAL, изменение kind и подмену финансового
снимка началом пробного. Платное подтверждение пробного запрещено. Исход вносит
преподаватель; менеджер не получает write-методов для исхода/фидбэка.
Отмена пробного всегда без списания, включая chargeable=true. Worker по отмене/
неявке возвращает текущую заявку в работу и создаёт один followup.

Worker повторно проверяет факты Finance/Schedule в БД и сохраняет receipt по ID
Outbox-события в Audit атомарно с изменением стадии. События расписания не
переоткрывают CONVERTED/LOST. По общему правилу пункта 7 опубликованная первая
оплата конвертирует и LOST; это техническая трактовка до отдельного уточнения
владельца, а не новое согласование. Снимается только архивирование ученика,
созданное самой потерей этой заявки. Ручного CONVERTED нет.

При потере заявки ученик без поступлений, распределений и аккаунта архивируется.
Метка времени на Lead позволяет при reopen снять только архивирование этой
операции; независимо архивированный ученик не восстанавливается автоматически.

CONTACT получает EMAIL по адресу заявки. Без email операция назначения завершается,
а dispatch сохраняется FAILED/NO_DELIVERY_CHANNEL. Контакты и фидбэк не попадают
в Audit/Outbox payload и логи. События содержат идентификаторы и безопасные статусы.

Summary использует тот же SQL в endpoint и дашборде. Сегодня определяется в
SCHOOL_TIMEZONE; trialsToday учитывает все попытки через trial_lead_id.
Конверсия — доля заявок когорты создания за последние 30 дней, уже получивших
опубликованную первую оплату, целое число базисных пунктов. Legacy CONVERTED
без достоверного converted_at не получает выдуманную дату конверсии.
Дашборд сохраняет единый read-only snapshot и использует семь команд из лимита 8.

Миграция сохраняет старые заявки. CHECK контакта добавлен NOT VALID для старых
строк; новые записи и последующие изменения обязаны иметь контакт. Удаления,
автоматического объединения, новых облачных БД и shadow reset не выполняется.
В соответствии с PHASE0_CHECKS.md синтетические DB suites и migrate dev/shadow
не запускаются на рабочей БД. Фактический migrate deploy и синтаксические проверки
отмечаются отдельно от unit/HTTP/browser evidence, без заявления полного DB gate.

Автозакрытие задач проходит OPEN → IN_PROGRESS → RESOLVED в одной транзакции.
SYSTEM обозначается system_resolved, без чужого resolved_by_staff_id. Старые
ограничения переходов MGR-07 сохранены; финансовым задачам такой допуск не предоставляется.
