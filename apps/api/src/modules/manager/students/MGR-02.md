# MGR-02 — CRM-список и карточка ученика

Реализация в локальном рабочем дереве, 31.10.2026. Основание — задача MGR-02 из
`docs/AI Coder Tasks — Модуль 2 Кабинет менеджера.md` и уточнение владельца в чате
о денежном балансе Ledger. Миграция подготовлена, к рабочей БД не применялась.

Миграция `20261031100000_mgr02_student_crm` сохраняет старые записи: version=1,
manager_note=NULL. Она добавляет ограничения, индексы и точечные runtime grants.
Триггер версий учитывает изменение CRM-полей также другими писателями, поэтому
они не обходят оптимистическую блокировку менеджера. Общий представитель семьи
не переименовывается: замена CRM-контакта завершает только свой PENDING-link и
создаёт новую контактную запись. Подтверждённые семейные связи сохраняются.

Индексы из ТЗ адаптированы к фактической схеме: связь `(manager_id, ended_at,
assigned_at, student_id)`, Student `(full_name,id)` и `(created_at,id)`, задачи
`(student_id,status,due_at,id)`, платежи `(student_id,registered_at,id)`. Индекс
`managerId,status` невозможен без дублирования вычисляемого статуса/назначения.
GIN по lower(full_name) создаётся только при уже установленном pg_trgm;
миграция не устанавливает расширение и не расширяет права runtime на DDL.

## Маршруты и безопасность

Все четыре endpoint-а используют ManagerRoute и существующие session/RBAC/CSRF
guard-ы. Нет новой аутентификации, имперсонации или обхода MFA. Нет роли ADMIN
в реальном enum; DIRECTOR и TECH_OPERATOR, а также STUDENT/TEACHER запрещены.

| Метод | Путь                                         | Результат                                                              |
| ----- | -------------------------------------------- | ---------------------------------------------------------------------- |
| GET   | /api/v1/manager/students                     | Страница списка, nextCursor или NULL                                   |
| GET   | /api/v1/manager/students/:studentId          | Карточка и STUDENT_PII_VIEWED в одной транзакции                       |
| POST  | /api/v1/manager/students                     | 201, создание без аккаунта, обязателен UUID Idempotency-Key            |
| PATCH | /api/v1/manager/students/:studentId/contacts | Контакты/заметка, version обязательна; конфликт → 409 VERSION_CONFLICT |

StrictInputDto — opt-in метаданные существующего DtoValidationPipe: body/query
новых DTO трансформируются и валидируются с forbidNonWhitelisted, ошибки → 422.
Обычные DTO сохраняют прежнее поведение. Некорректные boolean query не превращаются
в false. limit 1…100, по умолчанию 25; поиск 2…100 символов. Управляемые сервером
managerId/status/hasAccount и fullName в PATCH отвергаются. NULL очищает контакт
или заметку; отсутствие поля оставляет прежнее значение.

Нет сессии → 401; запрещённая роль → 403. Существующий core guard для отсутствующего
или неправильного Idempotency-Key возвращает 400 IDEMPOTENCY_KEY_REQUIRED; это
отдельно отражено в OpenAPI. Для данного POST mismatch тела с тем же ключом →
409 IDEMPOTENCY_KEY_REUSED; для старых команд прежний 422 не изменён.

GET/PATCH ID проходят assertStudentInPortfolio внутри транзакции. Чужой и
несуществующий ученик дают одинаковый 404 STUDENT_NOT_FOUND без чтения PII.
POST не принимает studentId; перечисление GET само ограничено портфолио.
Повтор POST проверяет принадлежность сохранённого studentId до выдачи cached
результата. После переназначения ученика прежний менеджер получает 404.

## Выборка и курсоры

Список — один параметризованный бизнес-запрос независимо от размера страницы.
Общий фиксированный pipeline session/MFA/RBAC имеет собственные запросы и не
входит в бюджет выборки списка. Нет отдельных запросов для каждой строки.

Прямое владение описано только ManagerScopeService. Его SQL-предикат получает
каноническое условие portfolioWhere, остальные фильтры добавляются через AND.
Поиск по имени/телефону/email параметризован; `%`, `_` и обратная косая черта
экранируются для LIKE. В список не выбираются немаскированные контакты или заметка.
Телефон — `***` и последние две цифры. Даты в ответах — ISO-8601 UTC.

hasOverdueTask учитывает OPEN/IN_PROGRESS с due_at < now. ExpiringSoon означает
действующий абонемент с концом в ближайшие 7 суток включительно; false тоже
явный фильтр. Одинаковые ключи сортировки разрешаются по UUID id, NULL идут
последними. Это keyset, без OFFSET.

Курсор шифруется AES-256-GCM, содержит pivot ID, время и fingerprint менеджера/
фильтров. В нём нет открытого ФИО/телефона. Ключ — MANAGER_CURSOR_SECRET или
существующий CSRF_SIGNING_SECRET, минимум 32 байта; TTL 30 минут. Менять limit
между страницами можно, менеджера/фильтры нельзя. Pivot проверяется в той же
scoped выборке; исчезнувший или недоступный pivot → INVALID_CURSOR/422.
Время курсора не фиксирует права: портфолио при каждом запросе проверяется заново
по текущему времени. Изменение данных между страницами не считается snapshot БД.

Единственный raw SQL executor — приватный read() в students.read.ts: только
заранее составленные параметризованные SELECT/CTE. Он отвергает write SQL.
ESLint запрещает raw execution в других manager-файлах и вне этого метода;
queryRawUnsafe/executeRaw запрещены. Это адресное уточнение запрета MGR-01,
позволяющее агрегатную сортировку без N+1. Prisma-записи защищённых учебных/
ledger-моделей по-прежнему запрещены, включая aliases/destructuring.

## Атомарность, аудит и PII

POST использует core CriticalCommand: SERIALIZABLE, максимум три попытки,
бизнес-запись + аудит + Outbox + сохранённый идемпотентный ответ атомарны. Повтор
с тем же ключом/телом получает тот же 201; другое тело → 409. TTL core — 48 часов.

PATCH и чтение карточки используют core TransactionService.runResult: Err после
записи конвертируется на границе ядра и откатывает транзакцию. Нельзя зафиксировать
частичную мутацию, вернув Err из callback. При отказе audit, Outbox или финального
чтения PATCH контакты, версия и события откатываются.

Аудит STUDENT_CREATED / STUDENT_CONTACTS_UPDATED содержит имена изменённых полей
и `[redacted]`, без ФИО/контактов/заметки. Outbox содержит идентификатор и имена
полей, без значений. GET пишет STUDENT_PII_VIEWED при каждом открытии; отказ аудита
не позволяет вернуть карточку. Ошибки data access — generic Result, без SQL/PII.
Карточки POST/PATCH отражены соответствующим аудитом бизнес-команды.
Оба новых manager-topic зарегистрированы в worker как observed events: они не
попадают в unknown-topic/DEAD и не отправляют незаказанные уведомления.

Карточка содержит до 5 ближайших уроков, до 10 платежей и до 100 открытых задач.
Если задач больше, openTasksTruncated=true; безлимитного массива нет. Учебный
срез — только разрешённые счётчики. Для ДЗ pending означает не сдано и ещё не
просрочено; overdue — отдельная категория. Тексты оценок, basis, комментарии,
содержимое работы и отчёта не выбираются и не включаются в DTO. Дополнительный
allowlist проекции защищает ответ от случайного расширения SQL.

## Денежный balance: уточнение владельца от 31.10.2026

balance — денежный Ledger-остаток, а не цена к оплате и не количество занятий.
Положительный знак означает неизрасходованный аванс, отрицательный — реально
отражённую проводками задолженность. Остаток не ограничивается снизу нулём.
Будущая неоплаченная цена или сама рассрочка не создают долг в этом read-model;
MGR-02 вообще не создаёт финансовых проводок.

Канонический read helper — finance/student-ledger-balance.sql.ts. Он считает
credit minus debit по CUSTOMER_ADVANCE для всех абонементов ученика, включая
исторические, только published_at/effective_at <= now. Исходные документы
распределений, списаний и возвратов однозначно связаны с его абонементами.
Распределения требуют подтверждённого поступления и утверждения директора;
непроведённые или ожидающие подтверждения суммы не прибавляются к balance.
Исходная запись, опубликованное сторно и замена складываются ровно по одному
разу; attribution корректировок наследуется от исходного документа.

В соответствии с реальной схемой PaymentReceipt.student_id — только CRM-контакт.
Нераспределённые средства семьи не приписываются этому ученику автоматически:
UNALLOCATED_FUNDS не смешиваются с его CUSTOMER_ADVANCE. Владелец явно утвердил
эту привязку 31.10.2026; см. docs/online_academy_manager_finance_distribution_clarification_2026_10_31.md.
Автоматического переноса/распределения средств нет. История карточки показывает
только распределённую ученику часть поступления, когда его контакт доступен
менеджеру, без общей суммы поступления или нераспределённого остатка семьи.

balance / balanceCurrency показывают валюту школы из SCHOOL_CURRENCY (MDL по
умолчанию). balances содержит отдельные строки всех встреченных валют, без
конвертации или суммирования разных валют. Все денежные значения — точные
Decimal-строки с четырьмя знаками; number и parseFloat не используются.

Последние распределения возвращаются отдельно в recentPayments: id=distributionId,
paymentId — ссылка поступления, amount — только часть, распределённая на абонемент
ученика. Дополнительно CRM-контакт поступления должен входить в портфолио менеджера.
AWAITING_APPROVAL — нет подтверждения поступления или одобрения распределения;
PENDING — отсутствует публикация поступления либо распределения; CONFIRMED — обе
публикации есть. Баланс не выводится суммированием этого массива. Нераспределённые
средства семьи и полные суммы общих поступлений в карточку не включаются.

## Проверки и границы доказательств

```powershell
pnpm --filter @online-school/db db:validate
pnpm --filter @online-school/api build
pnpm --filter @online-school/worker build
pnpm generate:client
pnpm generate
pnpm exec tsc -b packages/api-contracts --pretty false
pnpm test:mgr02
```

Набор manager-students / manager-students-http / manager-students-sdk проверяет
контракты, реальные Nest guard/pipe/interceptor/filter, replay, rollback, версии,
PII allowlist, денежные строки, курсоры/параметры SQL и бюджет запросов. Prisma
storage подменён; concurrency-тест не объявляется проверкой гонок PostgreSQL.
Синтаксический анализатор PostgreSQL отдельно проверил шесть вариантов list SQL,
card, balance и migration SQL; БД и тестовые данные для этого не создавались.

Prisma validate, целевые сборки/lint и генерация проходят. Попытка schema-only
migrate diff в установленном CLI не произвела SQL-артефакт и не принята как
доказательство миграции. Живое применение, SQL-план, runtime grants/trigger и
финансовая сверка на PostgreSQL не проверялись. PHASE0_CHECKS.md запрещает
одноразовый PostgreSQL; рабочая БД не изменялась. FND-GATE/production GO этим
инкрементом не закрываются.

В адресной регрессии обнаружены три старых unit-ожидания STU-07, разрешавших GET
подписки без активного доступа. Они приведены к уже действующему STU-11 (402);
приложение и его актуальные HTTP-тесты для этого правила не изменялись.

Итог: 200/200 адресных тестов в 10 наборах — MGR-01, MGR-02, student-context/
student-http и STU-07. Собственный набор MGR-02 содержит 64 теста. Прошли
API/worker/API-contracts compilation, адресный ESLint, Prisma validate и генерация
OpenAPI/Orval; девять финальных SQL-вариантов прошли syntax parse. Это не общий
project regression и не доказательство выполнения миграции на PostgreSQL.
